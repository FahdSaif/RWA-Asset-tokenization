# Data provenance

This file states plainly, for every data file in this directory, whether it
is **real** (sourced from an authoritative external body, with citation and
retrieval date) or **synthetic** (generated for this repository, with the
generator script and the reasoning behind the design choices).

| File | Real or synthetic | Notes |
|---|---|---|
| `fatf_lists.json` | **Real** | FATF "grey" and "black" list snapshot, dated. See provenance block inside the file itself. |
| `synthetic_transactions.csv` | **Synthetic** | Generated by `scripts/generate_synthetic_transactions.py`. See below for why. |
| `risk_model.joblib` | Derived | Trained artifact from the synthetic dataset above. Not checked into git (`.gitignore`); regenerated automatically the first time `TransactionRiskScoringAgent` runs, or explicitly via `python -c "from arca.layer1_intelligence.risk_scoring_agent import train_model; train_model()"`. |

## `fatf_lists.json` — real data

Source: FATF Plenary outcomes, 17–19 June 2026.

- https://www.fatf-gafi.org/en/publications/High-risk-and-other-monitored-jurisdictions/increased-monitoring-june-2026.html
- https://www.fatf-gafi.org/en/publications/High-risk-and-other-monitored-jurisdictions/Call-for-action-february-2026.html
- https://www.fatf-gafi.org/en/countries/black-and-grey-lists.html

Retrieved: 2026-09-23.

**This is a dated snapshot, not a live feed — and that is deliberate, not
an oversight.** The paper's own Problem Dimension II is that "compliance
logic, when manually encoded into smart contracts or application-layer
code, lacks the capacity to dynamically adapt to [regulatory] changes."
Hardcoding a "current" sanctions/grey-list snapshot into a public GitHub
repository would itself be exactly that anti-pattern: the file would start
going stale the day it's merged, silently, with no signal to anyone
downstream. FATF reviews these lists three times a year (February, June,
October); OFAC's SDN list changes multiple times a *week*.

The architecturally correct answer — and the one `arca/layer4_governance/
oracle_network.py` actually implements — is that this data should always
be pulled from a live, signed, multi-source oracle feed, with the Rule
Registry updated only through the governance-quorum path. This JSON file
exists so the demo and test suite have *something real* to exercise that
pipeline against without requiring live network access at test time
(important for CI reproducibility). Before using this repository for
anything beyond reproducing the paper's results, re-run the ingestion
against the live sources above (or wire up `oracle_network.py` to them).

We also looked into shipping a bundled snapshot of the official OFAC
Specially Designated Nationals (SDN) list (a real, public-domain, U.S.
government dataset — see https://sanctionslistservice.ofac.treas.gov/).
We did not, for two reasons: (1) OFAC's service applies bot-detection that
blocked programmatic retrieval from this build environment, and manually
transcribing ~20,000 rows is exactly the kind of stale, error-prone
static copy this architecture is designed to avoid; (2) more importantly,
a full SDN snapshot in a compliance-adjacent public demo repo would be
*more* likely to mislead (someone might use it as if it were current)
than to help. `scripts/fetch_regulatory_data.py` documents the real,
official endpoints and a ready-to-run fetcher for anyone running this
outside a network-restricted sandbox.

## `synthetic_transactions.csv` — synthetic, and why

Real account-level AML/CTF transaction data is confidential: it is
protected by bank secrecy law, by data-protection legislation (e.g. the
GDPR, Australia's Privacy Act), and — where it relates to an actual
Suspicious Activity/Matter Report — often by statutory non-disclosure
obligations on top of that. It cannot legally be published in a GitHub
repository, by us or by anyone else. This is exactly the gap the paper
itself names in Sec. VII ("Directions for Future Research"): empirical
validation on real transaction data is future work, contingent on
"engagement with regulatory authorities" and an actual institutional
deployment.

What we did instead: `scripts/generate_synthetic_transactions.py`
generates transactions from four latent behavioural archetypes (normal,
structuring, high-risk-corridor, rapid-layering), each parameterised
against publicly-documented FATF / Egmont Group red-flag typologies
(structuring near reporting thresholds, layering through many new
counterparties, exposure to FATF grey/black-listed jurisdictions), with a
*probabilistic* — not rule-based — label. The intent is a dataset with
genuine, learnable signal for the Transaction Risk Scoring Agent (it
reaches ROC-AUC ≈ 0.87 on held-out data — see `notebooks/
01_risk_scoring_model.ipynb`), without either (a) being real confidential
data, or (b) being a toy problem the model can memorize outright.

If you are adapting this repository for a real deployment: replace this
file and retrain (`train_model()`) against your own institution's
transaction history, under your own data-governance and model-risk
controls. Do not use `synthetic_transactions.csv` or the model trained on
it for anything beyond demonstrating the *architecture*.

## Refreshing regulatory reference data

`scripts/fetch_regulatory_data.py` documents the real, official data
sources this repository's Layer 4 Regulatory Oracle Network is designed
to consume in production (OFAC's Sanctions List Service API, FATF's
published lists), with a fetcher that will run against them from any
environment with normal (unrestricted) internet egress. It is not run as
part of this repository's test suite, precisely because tests should not
depend on live third-party network calls.
